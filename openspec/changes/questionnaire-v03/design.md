# 設計

## 資料 ownership 與版本邊界
題庫與抽題規則屬於 domain 純函式，不連 Supabase。場次的 `questionnaire_version`（文字欄位）是唯一的版本來源：
- `v0.1`：固定 8 題（既有）。
- `v0.2`：24 題題庫，凍結不動（題目、選項、配分、id 與抽題結果都不得改變）。
- `v0.3`：48 題題庫，新場次使用。

`selectQuestionsForSession(code, version)` 依版本挑題庫；人格計分、配對與成功率沿用同一組純函式，因此 v0.2 房間的結果與升級前逐字相同。成功率演算法以固定 mapping 指派（`v0.3 → v1`），未列入 mapping 的版本仍然 throw，不得 fallback。

## 為什麼不改人格演算法
人格以「達成率」（得分 ÷ 該房可得最高分）比較，同分時依 `PERSONA_PRIORITY`。這組函式由 App 與 session-service 以「題目清單」呼叫，沒有版本參數；若讓它依版本分岔，必須改動呼叫端，也會讓 v0.2 的行為有被誤改的風險。因此 v0.3 只從題目配分下手，v0.2 的計算路徑完全不動。

## v0.3 配分平衡原則
達成率比較會偏袒「出現次數少、配分集中」的人格，所以配分依下列原則設計：
1. 每個人格在每個類別都有出現，整體約出現在一半的題目；每題兩個選項各帶 2～3 個人格。
2. 每個人格的總配分質量（各題最高分加總）接近，避免某個人格的分母特別小或特別大。
3. 立場相反的人格放在相反選項（和平／逆風、近／遠、省／貴），貼近人格金句，不為了平衡而牽強配對。
4. `self-image` 固定入選，且 `very` 選項 id 必須保留（個人化文案與主持人畫面依賴該統計）；它的配分改成不偏袒任何單一人格。
5. 用 2 分與 3 分混搭降低「完全同分」，同分時沿用既有優先序，因此以模擬分布驗證優先序造成的偏差在容許範圍內。

## 驗證策略
- 結構測試：48 題、每類 8 題、id 唯一、皆為必答二選一、每個選項至少有一個配分、所有人格在每個類別都有配分。
- 版本相容測試：v0.2 題庫雜湊與 500 個房間的「抽題＋人格」摘要與升級前相同；v0.1 不變；v0.3 抽題穩定、每房 12 題、每類 2 題、含 `self-image`；v0.3 的成功率演算法已映射，未知版本仍 throw。
- 分布模擬測試：固定種子、30,000 個隨機房號與均勻隨機作答，比較 v0.2 與 v0.3 的十種人格比例；斷言 v0.3 最高與最低的差距不到 v0.2 的一半，且每種人格都落在合理區間。模擬結果寫進 PR。
- 建立場次測試：新場次寫入 `questionnaire_version` 為 v0.3。
- 完成前執行 typecheck、單元測試、E2E、build 與 OpenSpec strict 驗證。

## 風險
- 已存在的 v0.2 房間：版本欄位不變，題目與演算法不變；以黃金摘要測試守住。
- 進行中的 v0.2 房間在部署期間重新整理：仍由其版本欄位決定題目，不受影響。
- 同分優先序仍偏袒排序在前的人格：用模擬分布驗證，不通過就調配分而不是改優先序。
